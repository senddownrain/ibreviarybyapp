# Доступ для святароў: Firebase Spark

Flutter согласован с фактической реализацией `mybrev`, commit `7122bb2`:
`firestore.rules`, `src/utils/priestCode.mjs`, `src/utils/priestPolicy.mjs`,
`shared/priest-code-vectors.json` и `docs/priest-access.md`.
Cloud Functions, прежний priestApi и локальная проверка правильности кода не используются.
Веб-проект в рамках этой Flutter-реализации не изменяется и не публикуется.

## Auth и первоначальная активация

Именованный Firebase App `mybrev-priest` использует тот же Firebase project,
что основной App. Его Anonymous Auth не заменяет основную/администраторскую
сессию. Анонимная учётная запись создаётся только при активации, затем SDK
восстанавливает сохранённую сессию и автоматически обновляет ID token.
Firebase UID идентифицирует установку, но не является авторизационным секретом.

Нормализация v3: допускается только ASCII; пробел/tab/CR/LF убираются только
с краёв, буквы переводятся в верхний регистр, одиночные дефисы удаляются.
Алфавит `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, длина 24–64 символа.
Flutter вычисляет SHA-256 UTF-8 нормализованной строки. Совпадение с вебом
проверяется копией всех официальных тестовых векторов в `test/fixtures`.
Неправильный, но допустимый по формату код отвергают Firestore Rules.
Исходный код и proof не записываются в настройки, логи или локальные файлы.

`priestDeviceGrants/{uid}` создаётся с полями:
`uid`, `status: active`, `deviceName`, `client: Flutter`, `platform`, `label`,
`activatedAt`, `lastActiveAt`, `revokedAt: null`, `activationProof`.
Времена задаются `serverTimestamp`. Rules сравнивают proof с закрытым
`priestAccess/settings.activeCodeProof` и проверяют UID и допустимые поля.
Flutter не читает закрытые настройки. Необязательный контакт читается из
`priestAccessPublic/help.helpText`.

У grant нет срока окончания. При запуске проверяется его статус, а не старый
код. Смена кода не меняет существующее разрешение. Активность записывается не
чаще разрешённого Rules интервала в один час. Отозванный UID нельзя повторно
активировать: приложение показывает сообщение о связи с администратором.

Учётные данные хранит официальный Firebase Auth SDK. Дополнительный record в
`flutter_secure_storage` содержит только `verifiedUid` (подсказка интерфейсу)
и `pendingDisableUid` (намерение отзыва), без токенов и молитв. Старый HTTP record
удаляется при переходе. Полная потеря Auth/защищённых данных требует новой
активации; восстановление через Backup не гарантируется. Android backup/transfer
исключает shared preferences с Auth и защищённым record; пользовательские Hive
настройки сохраняются. Старые серверные grants приложение не удаляет.

## Firestore и каталог

Публичные `prayers` и `prayerCategories` читаются прежним основным клиентом.
С активным серверным grant добавляются `priestProtectedPrayers` и
`priestProtectedCategories`, с сохранением ID и устранением дублей. Защищённая
версия документа имеет приоритет. Все защищённые документы помечаются в памяти
`effectivePriestOnly`, включая наследуемые ограничения.

Существующие провайдеры каталога, дерева, поиска, избранного и reader используют
это объединённое представление. Отдельной вкладки или локальной базы для
священников нет. Ограничения учитывают `parentId`, теги, `categoryId` и
`categoryIds`; циклы и неизвестные родительские ссылки закрываются.
Прямой маршрут закрытого reader дополнительно проверяется сервером.
Истории чтения молитв в текущей архитектуре нет; отдельный обход через неё
не добавлен. Избранные ID остаются в пользовательских настройках и временно
скрываются при отсутствии доступа.

Публичные Firestore коллекции и Bundle/Manifest должны физически исключать
закрытые документы согласно миграции веб-проекта. Flutter сохраняет в прежний
Hive ContentStore только проверенное публичное представление; tombstones и
compaction удаляют перемещённые из публичного каталога записи. Обычная
синхронизация продолжает читать публичные документы Firestore и проверять хеши.
Закрытые коллекции не входят в список коллекций Bundle/Manifest обновления.

## Отзыв и офлайн

Закрытые материалы доступны только онлайн. Отдельный Firestore client имеет
`persistenceEnabled: false`, все защищённые get/query используют `Source.server`.
Для очистки SDK памяти client завершается; следующий запрос создаёт свежий
официальный platform delegate. Это нужно и для Chrome, где высокоуровневый
FlutterFire wrapper кешируется по имени App и иначе удерживает завершённый client.
Firebase App удаляется без signOut, сохранённая Auth-сессия восстанавливается
под прежним именем. Публичный Firestore client и его persistence не затрагиваются.

Listener собственного grant обнаруживает серверный отзыв. Отзыв, потеря сети,
переход в фон и неуспешное серверное чтение удаляют закрытые документы из
состояния и reader. Поздние ответы отбрасываются по поколению операции.
Офлайн не считается постоянным отзывом; при возвращении сети/приложения
восстанавливается прежняя сессия и повторяется серверная проверка.
Если связь с Firebase пропала при сохранённом подключении Wi-Fi, неуспешная
проверка автоматически повторяется с задержкой 5 секунд, увеличивающейся до
5 минут. После успеха повторы прекращаются; постоянного опроса grant нет.

«Выключыць доступ» требует подтверждения. Приложение сразу скрывает закрытые
материалы, сохраняет `pendingDisableUid`, отзывает свой grant (`status: revoked`,
`revokedAt: serverTimestamp`), затем выполняет signOut только именованного Auth.
Если сервер недоступен, намерение сохраняется и повторяется после подключения,
в том числе после перезапуска. До подтверждённого отзыва защищённые чтения
заблокированы. Если Auth-сессия потеряна при сохранившемся намерении отзыва,
UID сам по себе не позволяет отозвать старую установку: нужна помощь администратора.

Обычные молитвы работают офлайн как прежде. Уже увиденный/скопированный вне
приложения текст удалить невозможно. Материалы старых выпущенных APK невозможно
ретроспективно защитить. Полнота production миграции — условие выпуска.

## Проверки и выпуск

Результаты текущего прогона сохранены локально в `audit-evidence/priest-spark`; эта
папка содержит машинные логи и скриншоты и не входит в коммит.
Локальные Auth/Firestore Emulator используются с project `demo-rules`,
а не с production project. Правила для тестов копируются из согласованного
веб-проекта в `build/priest-spark/firestore.rules`.

Перед выпуском:

1. В веб-проекте завершить физическое разделение данных и пересоздать безопасный
   публичный Bundle/Manifest из полного backup; не публиковать неполную миграцию.
2. В Firebase Console включить Anonymous Authentication. Не включать автоматическое
   удаление anonymous accounts, которое может уничтожить долгосрочную Auth-сессию.
3. По отдельному подтверждению опубликовать согласованные Firestore Rules и
   создать закрытые settings с новым случайным кодом по веб-алгоритму.
4. Проверить production проект, квоты Spark, текущую версию публичного bundle
   и grants через административный интерфейс. В рамках этого задания production
   коды, данные и правила не изменяются.
5. Выпускать обычный APK с target `lib/main.dart`, без emulator/test dart-defines;
   выполнить `python tools/audit_priest_apk.py <APK>`.

Для локального Android интеграционного прогона: запустить Firebase Emulator
на Auth 9098 / Firestore 8088, screenshot helper `node tools/priest_spark_capture.mjs`,
затем `flutter drive --driver=test_driver/priest_access_driver.dart
--target=integration_test/priest_access_flow_test.dart -d <emulator>
--dart-define=PRIEST_USE_EMULATORS=true --dart-define=FIREBASE_EMULATOR_HOST=10.0.2.2
--dart-define=FIRESTORE_EMULATOR_PORT=8088 --dart-define=FIREBASE_AUTH_EMULATOR_PORT=9098`.
Первый прогон сохраняет тестовую отметку для двух следующих запусков: после
остановки процесса и после перезагрузки Android. Не переустанавливать APK между
этими фазами: повторная установка через `flutter drive --use-application-binary`
может удалить данные и Auth UID. Использовать `adb shell am force-stop`,
`adb shell am start`, затем подключить driver через `--use-existing-app=<VM URI>`
с новым адресом Dart VM из logcat и adb port forwarding. После последней фазы
тест отзывает свой grant и удаляет только собственные тестовые отметки.

На этой Windows-машине режим Android Emulator `-gpu host` после cold boot
давал ANR System UI, чёрные кадры и фрагменты старого framebuffer. Для проверки
обычного APK используется тот же AVD с `-gpu swiftshader`, без wipe-data.
На этом AVD корректный обычный запуск дополнительно подтверждён через
`adb shell am start -n by.mybrev.playtest2026/com.example.mybrev_flutter.MainActivity
--ez enable-impeller false --ez enable-software-rendering true`.
Это параметры диагностического запуска, подтверждённые установленным Flutter
engine; manifest и renderer обычного приложения не меняются. Нужна отдельная
проверка штатного аппаратного renderer на физическом Android перед выпуском.
