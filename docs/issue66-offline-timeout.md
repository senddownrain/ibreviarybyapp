# Issue #66: офлайн-таймаут при приёмке PR #62

## Заключение

Классификация **B: существующая проблема тестовой фикстуры main**, воспроизведённая на чистом main и PR в одинаковых условиях. Блокер связи с PR #62 можно снять. Это не заключение о полностью зелёном наборе и не гарантия прохождения при произвольной CPU-нагрузке.

`FakeRemote` синхронно пересчитывал хэши всего опубликованного корпуса при каждом чтении version pointer и collection manifest. В целевом тесте три публикации вызывали шесть полных проходов по 736 документам `days`, кроме других коллекций и отдельного прохода для нового bundle. Эта CPU-работа занимала большую часть лимита. При конкуренции за CPU тест превышает 30 секунд на обеих версиях. Таймаут не отменяет его Future: teardown закрывает Hive при незавершённом commit, откуда вторичный `Box has already been closed`.

В реальном протоколе remote manifest уже опубликован; фикстура повторяла подготовку этих серверных данных внутри бюджета клиентского теста. Объявление `fetchCurrent()` как async не делает его синхронные `_hashes()` прерываемыми. Длинные проходы задерживают обработку timer, поэтому timeout может быть напечатан позднее 30-й секунды; начавшийся затем commit сам по себе не доказывает зависание Hive.

Минимальное исправление находится только в `test/content_offline_test.dart`: хэши вычисляются один раз на коллекцию в пределах одного неизменного опубликованного снимка FakeRemote. Новая публикация создаёт новый remote и вычисляет собственные хэши. Они по-прежнему независимо получаются через `documentHash`, без использования хэшей ContentStore. Повреждённый download через `served` не меняет манифест. Добавлена детерминированная проверка этих гарантий. Корпус, assertions существующих тестов и таймауты сохранены.

## Измерения временными зондами

Зонды охватывали загрузку/декодирование bundle, копирование коллекций, вычисление хэшей, построение manifest, check/apply, commit, Hive put/putAll/flush/clear/deleteAll и teardown. Внешний sampler записывал CPU ticks/RSS тестового процесса, cgroup throttling и CPU pressure каждые 0,5 с. У двух первых обычных запусков sampler завершился из-за отсутствующего `cpu.pressure` в cgroup; их фазовые таймеры полные, resource samples отсутствуют. Перед нагрузочными запусками sampler исправлен на `/proc/pressure/cpu`.

Вложенные строки нельзя складывать: manifest включает hashing, check включает manifest, apply включает commit. Параллельные bundle decode spans также нельзя суммировать как wall time. Commit в нагрузочных столбцах включает завершение с ошибкой во время cleanup; до teardown завершённые commits заняли соответственно 70 и 136 мс. Нет доказательства, что fsync/Hive блокировали тест на десятки секунд.

В нормальных запусках на входе в teardown и после него нет отслеживаемых незавершённых Future. При нагрузке и на main, и на PR снимки на 29-й секунде (timer отрабатывает после синхронной CPU-работы) и на входе в teardown показывают одинаковую цепочку:

`test.publish.103 → updater.apply.103 → store.commit.103 → hive.staging.clear`

Эта цепочка заканчивается уже при cleanup после timeout. Время закрытия Hive само по себе мало. Это подтверждает вторичный характер ошибки закрытого Box и отсутствие отмены Future таймаутом package:test. Изменение teardown или production commit ради маскировки этой ошибки не делалось.

## Контролируемое воспроизведение

Все команды выполнялись последовательно, в отдельных процессах и worktree, с одинаковым окружением и стандартными таймаутами. Нагрузка — пять одинаковых Python CPU workers в том же двухъядерном cgroup, начиная с появления целевого теста; каждый ограничен 120 с, все завершаются при окончании команды. Это воспроизводимый ресурсный стресс, а не утверждение, что в историческом полном прогоне работали такие workers.

| Исходный код / условия | main: exit / время команды | PR: exit / время команды |
| --- | --- | --- |
| Целевой тест, временные зонды, обычный запуск | 0 / 17,621 с | 0 / 17,573 с |
| Целевой тест, зонды и 5 workers | 1 / 39,050 с | 1 / 41,873 с |
| **Целевой тест, исходные файлы без зондов, 5 workers** | **1 / 47,923 с** | **1 / 47,979 с** |
| Тот же стресс после локального кэша, без зондов | 1 / 38,023 с | 1 / 35,683 с |

**Чистый main без зондов** воспроизводит первичный `TimeoutException after 0:00:30` и следующий `HiveError: Box has already been closed`, как PR. В raw-запусках тестовый процесс накопил 15,82 / 15,24 CPU-секунды за 43,15 / 43,27 с наблюдения. Cgroup throttled time вырос на 43,78 / 44,14 с. После кэша CPU-секунды уменьшились до 10,51 / 11,83; stress-test всё ещё превышает лимит. Эти отрицательные результаты сохранены, лимиты не увеличены.

Это доказательство **B**, а не заявление об устранении любого инфраструктурного ограничения по критерию C. Локальный кэш устраняет лишнюю повторную работу; оставшиеся полные публикации и хэши нового bundle по-прежнему требуют CPU. Бесконечно наращивать кэш между публикациями или сокращать реальный корпус ради прохождения искусственного стресса не стали.

Календарный #64 появился в main позднее и не переносился в эту ветку.

## Границы вывода и scope

Точный источник CPU-конкуренции в историческом `pr-full.txt` восстановить нельзя: тогда не было resource samples. Здесь доказан тот же отказ на чистом main при воспроизводимых эквивалентных условиях и измерен преобладающий расход времени. Не утверждается, что причиной был конкретный браузер, GC или незавершённая работа другого файла. Сам префикс не является надёжным триггером отказа.

Production ContentStore/Updater, HiveService и миграция, псалмодия, терминология, календарь, UI, Firestore, bundle и зависимости не менялись относительно `c78eaf7`. Все временные зонды удалены с проверкой исходных SHA. Нет merge, релиза или публикации. Новый визуальный аудит не нужен для изменения тестовой фикстуры; нативные проверки не заявляются.
