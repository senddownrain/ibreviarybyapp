## Безопасность миграции Hive

Первоначальный `_load()` запускал `_box.put()` и игнорировал Future. Hive меняет in-memory keystore до завершения записи; чтение нового значения из памяти не доказывает успешного сохранения. Ошибка записи не передавалась инициализатору. Это подтверждённый риск наблюдения результата записи и источник проблем FakeAsync.

При этом потеря данных при обычном `await Hive.close()` **не выводится автоматически** из отсутствия await: VM backend Hive 2.2.3 сериализует `writeFrames`, `flush` и `close`. Исправление основано на явном контракте завершения/ошибок, а не на недоказанном утверждении, что любое нормальное закрытие теряло настройку.

Минимальная реализация:

1. `HiveService.init()` после открытия settings определяет режим тем же чистым resolver. Если нужен новый ключ, выполняет `await settings.put(...)`, затем `await settings.flush()`. Существующий `main()` уже ожидает `init()` до `runApp`/ProviderScope.
2. `_load()` только читает; создание или пересоздание ProviderContainer не начинает I/O.
3. Общий `_save()` больше не перезаписывает псалмодию при изменении других предпочтений. Единственный writer после init — явный `setPsalmodyMode()`. Поэтому старый второй контейнер, сохраняющий избранное, не возвращает устаревший режим.
4. Setter обновляет Riverpod немедленно и завершает прежний `Future<void>` после put + flush. Публичный интерфейс не изменён.
5. Удалены две временные подготовки провайдера в фикстурах: теперь сам production init даёт нужную гарантию до начала FakeAsync.

Нет `sleep`, синхронного ожидания или новой системы миграций. Ожидание диска асинхронное. Ошибка put/flush распространяется через существующий Future инициализации. Валидный новый ключ не перезаписывается; старые ключи и другие настройки сохраняются. При повторном init запись не повторяется.

Тесты используют настоящие временные Hive-файлы. Проверены четыре старые комбинации, частичные/неизвестные значения, приоритет нового ключа, установка поверх закрытой старой базы, полный preferences map, реальное повторное открытие, немедленное закрытие **сразу после init без дополнительного flush/паузы/провайдера**, параллельное изменение избранного из второго контейнера и многократная инициализация без событий записи.

Если ОС завершает процесс **до окончания init**, миграция ещё не объявлена завершённой: старые ключи остаются и на следующем запуске детерминированно разрешаются снова. Деструктивного флага «миграция выполнена» нет. Сбой питания/носителя вне гарантий Hive не тестировался и не обещается.

Заключение: в пределах нормального async lifecycle и гарантий Hive миграция безопасна; успешное завершение init теперь означает завершённую и запись, сброшенную на диск через flush. Остальные пользовательские данные миграция не сбрасывает.

## Таймаут офлайн-контента: результат #66

- Все remote-ответы в этом файле — `FakeRemote`, работающий с локальными maps. Firestore для воспроизведения не использовался.
- Каждый test создаёт свой временный каталог Hive; сравниваемые команды выполнялись в отдельных процессах и двух изолированных worktree. Default concurrency — один test process.
- `openWithBundle()` ожидает загрузки всех коллекций. Изолированные прогоны целиком прошли на обеих версиях. Самостоятельного зависания teardown в них не найдено.
- В failed full-run сначала сработал timeout, затем незавершённый Dart Future продолжил commit после закрытия Hive в teardown. Поэтому `Box has already been closed` в этом логе — вторичная ошибка; по ней нельзя заключить, что первопричиной был deadlock Hive.
- `_commitTail` сериализует commits; `ContentStore.idle()` документирован как ожидание preload/load, а не всех commits. Код этих механизмов не менялся. Изменять его в PR без доказанного причинного дефекта не стали.
- Новые зонды показали: FakeRemote hashes занимают 9,7–9,9 с из 12,3–12,6 с целевого теста в обычном запуске; при нагрузке — 29,3–33,4 с. Нормальные три commits суммарно занимают 34–39 мс. CPU-доминирующая фикстура объясняет превышение 30-секундного лимита под нагрузкой на обеих версиях.
- Новая миграция завершается до ContentStore/provider startup; `_load()` не пишет. Измеренные put + flush — 15 мс обычно / 58 мс при нагрузке. На чистом main такой миграции нет, но тот же отказ воспроизводится.
- Исходный тест без зондов воспроизвёл timeout и вторичную ошибку Hive на main 6b74fbe и PR c78eaf7 с одинаковыми пятью ограниченными CPU workers. Кэш одной публикации уменьшил работу, но этот искусственный стресс всё ещё превышает лимит; это отрицательное наблюдение сохранено. Обычный весь файл с правкой: **38 passed на обеих версиях**. Источник CPU-конкуренции исторического full-run ретроспективно не установлен; доказательство независимости — воспроизведение того же отказа на чистом main, а не успешный одиночный retry.
- Временная инструментализация удалена с проверкой исходных hashes. Production ContentStore/Updater, Hive и таймауты не менялись. Итог по критерию B, включая последовательный префикс и новые проверки, описан в [отдельном отчёте](issue66-offline-timeout.md).
